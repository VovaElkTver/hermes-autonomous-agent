# Claims Harness — внешняя оракульская проверка аналитической работы агента

Версия: 0.1.0 (этап 1) · Дата: 2026-10-22 · Статус: draft-PR

## Зачем

Директивы Архитектора (20.10):
- «важнее реально пошаговый анализ, а не я_взял_10_из_100»;
- «грех Hermes: сам себя оптимизирует и считает скрипт успешным по отсутствию
  кода ошибки, а не по качеству».

Агент, проверяющий собственную аналитическую работу (суммы по xlsx, разбор
донора), склонен: (а) сузить множество работ («я проверил 10 из 100»), (б)
считать успехом отсутствие падения скрипта, а не качество результата. Claims
harness убирает обе проблемы, вынося оценку **вне кандидата**.

Схема донора: `github.com/gepa-ai/terrarium` — EvalServer как единая точка
бюджета/оценки, которую исполнитель не может обойти. Terrarium берётся как
**донор схемы**, а не как зависимость (см. ограничения).

## Три механизма

### Механизм 1 — ПОПУЛЯЦИЯ
В контракте шага указывается множество работы, которое **ПЕРЕЧИСЛЯЕТ харнес**
(файлы клона / строки БД / листы xlsx / страницы PDF), а не агент. Выборка —
явное решение с записью. Покрытие считается по trace сессии (какие файлы
реально читались). Молчаливая подмена популяции ловится как класс.

### Механизм 2 — ПРЕДИКАТЫ
Выход агента оформляется как утверждение с машинно-проверяемым предикатом.
Харнес прогоняет предикат по **ВСЕЙ** популяции и возвращает распределение
исключений (например, «15 файлов с суммой в другой ячейке из 100»). Агент
обязан объяснить каждый контрпример или сузить утверждение.

### Механизм 3 — ОРАКУЛ ВНЕ КАНДИДАТА + БЮДЖЕТ НА СЕРВЕРЕ
`eval_fn` заморожена и не видна исполнителю. Счётчики eval на стороне харнеса
(terrarium: single budget choke point). Каждая оценка проходит через единую
точку `FrozenOracle.evaluate()`; после исчерпания бюджета — `BudgetExhausted`.

## Модель данных

- `Item` — атомарная единица работы (файл/строка/лист/страница).
- `Population` — детерминированное перечисление, которым владеет харнес.
- `Trace` — что кандидат реально прочитал → `Coverage(covered, missed, extra, ratio)`.
- `Claim` — `statement` + `predicate: Item -> ItemResult`.
- `ClaimResult` — `passed`, `counterexamples[]`, `coverage`, `score`, `score_meta`.
- `FrozenOracle` — замороженный оценщик + бюджет; `eval_fn` спрятан в `_ev`.

Ключевой инвариант: **предикат прогоняется по полной популяции харнеса**,
независимо от trace кандидата. Контрпримеры на непрочитанных элементах — это
«silent-substitution catch».

## Два класса работ (прототип)

### 1. xlsx-колонка с суммами (пример Архитектора)
- Популяция: все `*.xlsx` в директории (перечисляет харнес).
- Утверждение: «C1 равно сумме столбца A».
- Внедрённый контрпример: в 15 из 100 файлов сумма лежит в C2, а в C1 —
  неверное значение → харнес находит все 15 и выдаёт их построчно.

### 2. Донор-разбор с coverage по trace
- Популяция: все исходники донора (например, `*.py`).
- Агент читает подмножество; покрытие считается по trace.
- Контрпримеры в непрочитанных файлах ловятся харнесом; неполное покрытие
  помечается как `incomplete_coverage`.

## Формат отчёта
Каждый контрпример — отдельная строка. Без «в основном». Поля detail (напр.
`expected_sum`, `c1_value`, `sum_found_at`). Отдельный блок — контрпримеры на
непрочитанных элементах.

## Этап 2 (после этапа 1)
GEPA крутится **ЗА** замороженным харнесом (вместо самонаписанной метрики):
самоулучшение скилов с внешним счётом. Terrarium — донор схемы, не зависимость.

## Ограничения
- Не внедрять DSPy/terrarium-рантаймы.
- stdlib + то, что в venv (xlsx — только stdlib: zipfile + xml).
- Каждый контрпример — отдельная строка отчёта.

python3 -m unittest discover -s tests -v   # 13 тестов, all ok
