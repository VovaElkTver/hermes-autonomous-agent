# Живучесть управляемой автономии (рестарты, форки, алерты)

Статус: реализовано, live с рестарта 15.11 09:40 МСК (коммит `69755cd31e`
и предшествующая цепочка planning-multistage). Авторство правок — @rtx5090 по
аудиту `controller-claims-v1.md` (6 предъявов подтверждены, Вл 15.11).

Документ описывает, как форк переживает перезапуски гейтвея при живых
планировочных потомках, кто владеет тикером автономии и почему некоторые
алерты кричат часто, а другие — раз в час. Для машинных контрактов см. скилл
`fork-ops` (бандл `skills/autonomous-ai-agents/fork-ops/`) — он едет с
инсталлом и апдейтами ко всем нодам форка.

## Задача

Тяжёлое планирование едет фоновыми fork-ветками (дети процесса гейтвея).
Рестарт гейтвея — штатная операция, но 14.11 серия рестартов ампутировала
живых детей: SIGTERM уходит systemd'у, а не нашему счётчику работ. Ответ
сделан трёхслойным, кодом:

### 1. Drain-aware рестарты

- Скрипт `~/.hermes/scripts/gw_cycle_planning.sh` (v2): берёт бут-эпоху из
  `ActiveEnterTimestamp`, считает по `events.jsonl` форки, созданные после
  бута без терминального события, ждёт их завершения до `$1` секунд
  (по умолчанию 600) и только потом делает stop/start.
- systemd drop-in `TimeoutStopSec=600`: стенка остановки не меньше легального
  рантайма ребёнка (бюджет планирования 480 с).
- Запускать вручную можно detach'ем (transient-таймер/свой scope), чтобы
  смерть инициатора не отменяла рестарт.

Терминальные события форка в `events.jsonl`: `planning.fork.created`,
`planning.fork.joined`, `planning.fork.failed`, `planning.fork.spawn_failed`
(у каждого есть `branch_id`). Нет терминального события — форк считается живым.

### 2. Boot-sweep = констатация, ретрай за человеком

При каждом старте свип (`sweep_orphaned_planning_forks`) находит строки веток,
которые родитель потерял при прошлом рестарте, ставит им `status='joined'`,
кладёт work-note родителю и журналирует `planning.fork.joined`
(`join_strategy=boot_sweep`). Автоматического перезапуска оборванной задачи
НЕТ: решение о ретрае принимает человек. Инвариант: свип обязан выдать
терминальное событие по каждой сироте — иначе дрейн-тулинг следующего
рестарта зависнет, считая её живой.

### 3. Владение тикером: flock + owner-row + reclaim-watch

Тикер автономии — синглтон: flock в `~/.hermes/run/controller-ticker.lock`
плюс CAS-строка `kind='owner'` в `ctl_ticker_heartbeat` (переживает
reload/fork/Windows). Третий слой — reclaim-watch (демон-поток, период
60 с): если локального живого тикера нет, а держатель записи мёртв (или его
строка протухла >2× pump-интервала), владение забирается рантаймом, без
рестарта гейтвея; факт — событие `ticker-reclaimed` + шаблонный алерт
`ticker-reclaim`.

Асимметрия, осознанная и принятая: чужой мёртвый pid определяется мгновенно;
залипший СВОЙ поток тикера (pid жив!) подхватывается только по протухшей
строке (>600 с).

### 4. Громкий гейт конфигурации

Сочетание `controller.enabled=true` и плагина в `plugins.disabled` раньше
тихо пропускало плагин (DEBUG) — автономия выглядела включённой, но не
работала. Теперь загрузчик пишет WARNING с прямым текстом, что убирать из
какого списка. Автономия молча не выключается.

### 5. Алерты: смена дайджеста против лестницы повторов

`maybe_alert` стреляет всегда при ИЗМЕНЕНИИ дайджеста текста. Неизменный
дайджест повторяется только при `backoff_s > 0` по растящемуся окну
(`backoff_s × 2^count`, кап сутки):

- human-gates: базовое окно 1 час — постоянные гейты напомнятают ежечасно,
  а не каждый пятиминутный тик насоса (инцидент «56→01→06 минут»);
- `backoff_s=0` (pump-stale, machine-park, resume-interrupted…) — намеренно
  эскалируют каждое окно; глобальный дефолт не вводить;
- восстановление чистит леджер (`clear_alert`) — рецидив снова новость.

Шаблоны предупреждений — только через `ALERT_TEMPLATES`, никаких inline
f-строк в цикле.

## Где что лежит

| Артефакт | Расположение |
|---|---|
| Реестр веток | `state.db` таблица `session_branches` (`status`, `join_strategy`, `joined_at`) |
| Живучесть тикера | `state.db` `ctl_ticker_heartbeat` (`pump`, `watchdog`, `owner`, `ticker-start/stop`) |
| Леджер алертов | `state.db` `ctl_alert_state` |
| Поток событий форков | `~/.hermes/planning-runs/events.jsonl`, `works.jsonl`, `run-NNNN/` |
| Дрейн-скрипт | `~/.hermes/scripts/gw_cycle_planning.sh` (v2) |
| Стенка systemd | `~/.config/systemd/user/hermes-gateway.service.d/timeout.conf` |
| Машинная памятка | skill `fork-ops` (поставляется инсталлом/апдейтом) |
