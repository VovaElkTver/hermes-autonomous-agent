# Аудит последствий: fork/join вместо карточного слоя в write-dialog

## Находки

**[КРИТИЧНО] — не решена маршрутизация ответа в ветку — п.1, п.3, тесты 5a/5b — весь контур управления держится на факте «сообщение человека попало в ветку wd:<key>», но правило привязки входящего сообщения к ветке нигде не задано (по комнате? по reply? по ключу?). Это тот же шов ingress, где прямо сейчас теряется provenance при пересборке событий — то есть самая проблемная зона системы стала несущей конструкцией новой фичи. Блокирует п.1, п.3 и осмысленность тестов 5. Смягчение: до кодирования зафиксировать правило привязки письменно + RED-тест на каждый путь пересборки (debounce-склейка, media-fusion, reply-context), а не только на text batch.**

**[КРИТИЧНО] — «обход гейта» + предикат над любым role=user = автоматическая запись без контроля автора — п.3 — если в комнате после вопроса ветки пишет кто угодно (мультиюзер-комната), предикат срабатывает, и конфиг перезаписывается в обход авторизации. Примеры в плане — правки `~/.hermes/config.yaml`, т.е. цена ошибки высока. Смягчение: whitelist авторов ветки при создании; для необратимых записей — intents/needs_approval, как обещано в fork_explore, иначе это декларация, а не механизм.**

**[СЕРЬЁЗНО] — нет защёлки предиката (idempotency) — п.3 — тик 1 Гц, исполнение через главную сессию заведомо дольше тика; переход состояния ветки (open→fired→joined) не описан → возможны многократные срабатывания и многократная запись файла. Метрика: duplicate_fires, должна быть строго 0. Смягчение: атомарный переход состояния ветки до исполнения + перепроверка предиката непосредственно перед записью (заодно закрывает гонку «правка пришла между тиком и записью»).**

**[СЕРЬЁЗНО] — параллель «6 ∥ 1→2→3→4» при смене диагноза по ходу — раздел «Порядок» — зависимость п.1–4 от п.6 обосновывалась неверным диагнозом; новый фикс-кандидат (шов пересборки) трогает общий адаптерный путь всех сообщений и может оказаться таким же промахом, как первый. Тогда п.7 упрётся в живой баг: ответы в ветки будут отклоняться, фича умрёт на приёмке, а давление «уже готово» превратит обход гейта из временной меры в постоянную. Смягчение: жёсткий гейт — п.7 только после зелёного PR и деплоя фикса; параллелить допустимо лишь рефакторинг хранилища (п.1–2).**

**[СЕРЬЁЗНО] — потеря сообщения превращается в вечное молчание — п.3, п.5 — документированный класс отказов системы — съеденные сообщения (09:32, 10:00, today). Таймеры план отверг принципиально, но взамен не предложил детектор отсутствия прогресса: если ответ съеден ingress, предикат не сработает никогда и никто не узнает. Смягчение: watchdog-сверка session DB ↔ лог matrix (это ровно разрешённый аксиомой источник) + метрика hung_branch_age.**

**[СЕРЬЁЗНО] — pinning компрессии без жизненного цикла веток — тест 5e — активная ветка держит watermark родителя, но механизм старения/закрытия забытых веток не задан. Монотонный рост открытых веток → невозможность компрессии → деградация контекста и стоимости родителя. Метрики: возраст открытых веток, число старше N часов, глубина watermark. Смягчение: TTL + автоперевод в note или ручной sweep.**

**[СЕРЬЁЗНО] — скрытое допущение о доступности главной сессии — п.3 — «исполняется главной сессией» предполагает, что она может принять инъекцию вызова в любой момент. Занятая сессия = либо задержка записи, либо вытеснение текущей работы — риск вернуть блокировку, которую fork-схема как раз убрала. Способ инъекции не описан. Смягчение: очередь задач с приоритетом; измерять latency fire→execute.**

**[СРЕДНЕ] — противоречие с собственной аксиомой — Аксиома vs п.1 — «журналы и базы hermes — косвенные улики», но состояние диалога теперь живёт только в базе hermes. Либо аксиому сужать (только forensics ingress), либо закладывать сверяемость с логом matrix с первого дня — иначе следующий же расследовательский цикл упрётся в недоверие к хранилищу, на котором построена работающая фича.**

**[СРЕДНЕ] — big-bang рестарт при уже существующем перекосе — п.7 — «плагин на диске новее загруженного» означает, что холодный рестарт поднимет весь накопленный дельта, а не только эту фичу; whoami-проверка — слишком тонкий пост-контроль. Откат = ещё один рестарт с revert, история диалогов за окно обратно в JSON не выгружается (миграция односторонняя). Смягчение: инвентаризация diff диск/память до рестарта, окно низкой нагрузки, пост-мониторинг rejection-rate по логу matrix за час.**

**[СРЕДНЕ] — нет производственных метрик успеха — п.5 даёт функциональные тесты, но критерии «план не работает» в проде не определены. До: baseline rejection-rate `authorization_home_without_provenance`, латентность диалога в JSON-схеме. После: fired/joined/discarded/abandoned, duplicate=0, p95 вопрос→детект, hang-age, токены/диалог (join-note — дополнительный LLM-вызов на каждый диалог).**

**[МЕЛКО] — тест 5b проверяет «диск не тронут» компонента, который п.2 удаляет; переформулировать как «нет записей вне session DB». Имена `wd:<key>` из file:-путей требуют экранирования; переименование ветки п.6 — проследить, чтобы forensic-артефакты (RED-тест, worktree) остались связными.**

## Вердикт: GO-WITH-CONDITIONS

Направление рабочее (примитивы существуют, тесты на реальном пути, коррекция диагноза задокументирована), но три решения не приняты и без них реализация создаст тихие отказы, а не явные.

**Top-3 до запуска:**
1. **Зафиксировать правило привязки и авторизации ответов в ветку** (кто и какое сообщение считается ответом; перенос provenance через пересборку) — без этого п.1/п.3 нереализуемы корректно, а п.7 небезопасен.
2. **Жёсткий гейт п.7 за зелёным фиксом ingress (п.6)** — параллельность ограничить хранилищем; фича не катится на живой гейтвей поверх известного бага приёма.
3. **Полный жизненный цикл ветки: защёлка предиката (однократное срабатывание), TTL/GC заброшенных веток, watchdog сверки session DB ↔ лог matrix** — с метриками duplicate/hung/abandoned, вводимыми одновременно с фичей, а не после.
