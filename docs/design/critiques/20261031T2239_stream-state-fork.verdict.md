## ВЕРДИКТ

Интерпретация принята наполовину: топологическая привязка к префиксу, fork как единственное средство приёмки и main-как-оркестратор — рабочая схема; но «реплика исчерпывает вердикт» и «открытый форк = глобальный мораторий на фронт» в текущей формулировке ломаются на первом же уточняющем вопросе владельца — механизм в этих двух узлах нужен другой.

---

## Машина состояний потока

**Правило классификации реплики владельца в форке (центральный узел):**
[КРИТИЧНО] «Реплика исчерпывает вердикт» внутренне противоречива: уточняющий вопрос — тоже реплика, но он не исчерпывает, а продлевает приёмку. Если любая реплика = вердикт, то «а почему тут так?» — это отклонение? Классификация отдаётся агенту на угадывание → ложное принятие по случайному «ок». Правило: три класса — **ПРИНЯТЬ / ОТКЛОНИТЬ / УТОЧНИТЬ**; неоднозначная реплика всегда = УТОЧНИТЬ (консервативно, цена — лишний круг, а не ложное закрытие). Merge-back инициирует агент, владелец имеет право вето *после* слияния — вето = новый форк на расширенном префиксе (revert через топологию, без id).

| Состояние main | Событие входа | Агент может | Агенту запрещено | Риск |
|---|---|---|---|---|
| **W0 РАБОТА** | старт / закрытие последнего форка | работать, расширять фронт, открыть форк приёмки | объявлять этап закрытым без форка | — |
| **W1 ПРИЁМКА** (ровно один открытый форк F) | FORK_OPEN | отвечать в F, вести main-протокол | закрывать любые работы, расширять фронт, открывать *второй sibling*-форк | блокировка всей трубы на одного человека |
| **W2 СЛИЯНИЕ** | реплика класса ПРИНЯТЬ в F | перенести хвост F в main как переход, опубликовать эхо в main | тихо слить без эха | окно вето до следующего события |
| **W3 ЗАВИСАНИЕ** (F открыт > T1) | таймер | одно напоминание **внутри F** по T1; по T2 — закрыть F без слияния, переход в main «форк закрыт без слияния», возврат в W0 | само-принятие, «тихое» удаление форка | см. ситуации |
| **W4 ОРКОСТРУКЦИЯ** | команда владельца в main | исполнить команду, при конфликте с F — один ограниченный вопрос в F («это про предмет форка?») | начинать новое_work поверх висящего форка без пометки | — |

**События:** FORK_OPEN, REPLICA_IN_FORK (классифицированная), MERGE_BACK, CLOSE_NO_MERGE, TIMER_TICK, OWNER_CMD_IN_MAIN.
[МЕЛКО] Таймер — экзогенное событие, нарушает чистоту «только структурные движения». Допустимо, но задокументировать: без него W1 — вечный дедлок.

**Ключевой инвариант:** [СЕРЬЁЗНО] параллельные sibling-форки запрещены. Два форка с перекрывающимися префиксами при merge-back дают конфликт, который без id нечем разрешить, кроме порядков создания — а это уже скрытые ординалы. Параллельность — только через вложенные форки (суб-приёмки), там топология дерева честная.

## Seam-лист

1. **`session_branches` (state.db)** — де-факто и есть «реестр открытых форков», уже с ключами. [СЕРЬЁЗНО] Тезис «никаких id» реализуем только на уровне протокола (что видит человек); на уровне хранения ключи были, есть и будут — иначе невозможны ни GC, ни восстановление после падения. Это надо зафиксировать явно, а не делать вид.
2. **Sticky-lock /forkb** — держит *маршрут участника*, а не *состояние приёмки*. Ничего из «запрещено расширять фронт / закрывать работы» существующая механика не энфорсит — это конвенция в цикле агента. [СЕРЬЁЗНО] «Запрещено» без энфорсмента = зависит от дисциплины модели; проверять метрикой main-purity.
3. **Префикс форка: снапшот или живой линк?** Не сходится: если /fork копирует контекстное окно (а не весь транскрипт), «чекпоинт всего префикса» молча обрезается лимитом контекста. Если живой линк — правки main после форка текут в форк и убивают топологическую привязку. Проверить до внедрения. [СЕРЬЁЗНО]
4. **gateway_routing + resume_pending/auto-resume** — точка split-brain: если sticky-мэппинг держится в памяти процесса, рестарт на resume отправляет реплики владельца в main, агент думает, что идёт приёмка. Реплика «в тему» и реплика «мимо темы» неразличимы для классификатора. [СЕРЬЁЗНО]
5. **Matrix thread-root** — якорь топологии. Redaction/редактирование корня или старых сообщений main переписывает префикс задним числом. [СРЕДНЕ] Нужен запрет edit/redact в main хотя бы конвенцией.
6. **Чего нет:** классификатора реплик (хоть словесные маркеры), таймеров T1/T2, журнала переходов main (им может быть сама лента — переходы как сообщения, без отдельного хранилища).

## Провалидные ситуации

- **Молчание владельца в форке.** W1 по построению — дедлок: труба стоит, виноват молчащий. Без таймаута это главный режим отказа всей схемы. Лечение: T1 напоминание в форке, T2 закрытие без слияния. Самопринятие запрещено — иначе приёмка фиктивна. [КРИТИЧНО]
- **Владелец правит main, не глядя в форк.** Префикс форка заморожен, правка живёт после точки форка → merge-back накладывается на изменённую main. Без id rebase невозможен; арбитр — агент, а это скрытое допущение. Лечение: W4 — один уточняющий вопрос, при конфликте форк сначала закрывается (merge или сброс). [СРЕДНЕ]
- **Несколько открытых форков.** См. инвариант: sibling'ы — нельзя, вложенные — можно. Иначе порядок слияний становится неявным реестром с ординалами, что хуже явного. [СРЕДНЕ]
- **GC зависших форков.** Закрытие без слияния: итоговое резюме агента — внутрь форка, в main — одна строка перехода. Трогаем только закрываемый форк, никакой глобальной ревизии — реестр задним числом не вырастает. Память об отклонении живёт в закрытом треде (корпус тредов = память), поиск — по цитате/моменту открытия, не по номеру. [СРЕДНЕ]
- **Не превратить в реестр id:** в текстах для человека — ссылки только цитатой или «форк, открытый после такого-то сообщения»; нумерация в протоколе запрещена; ключи state.db наружу не вылезают. [МЕЛКО] Дата/цитата — квази-id, и это честнее отрицать.

## Метрика (топологическая, без реестра)

- **Медиана времени в W1** (открытие форка → merge/close) — латентность приёмки, хвост распределения показывает узкое горло владельца.
- **Конверсия форков**: доля merge-back от всех закрытий; отдельно — доля зависших по T2.
- **Глубина уточнений**: реплик до вердикта на форк — трение приёмки.
- **Rework-прокси**: доля новых форков, чей префикс пересекается с недавно закрытым без слияния (память об отказах работает/нет).
- **Main-purity**: доля сообщений main, являющихся переходами/командами, от общего числа — соблюдение протокола обеими сторонами.
- **Misroute-инциденты**: реплик не в тот тред за неделю — здоровье sticky/routing после рестартов.
[СРЕДНЕ] Базовую линию снимать немедленно, до рефакторинга — иначе «стало ли лучше» неответимо.

## ИТОГ: GO-WITH-CONDITIONS

**Top-3 условий:**
1. Инвариант «один открытый форк приёмки»; параллельность — только вложенными форками. Без этого топология префиксов разваливается, а порядок слияний станет скрытым реестром.
2. Консервативная классификация реплик (неоднозначно = УТОЧНИТЬ) + эхо merge-back в main с правом вето/переоткрытия новым форком. «Реплика исчерпывает вердикт» в исходной формулировке — источник ложных принятий.
3. До внедрения: верифицировать снапшот/линк префикса в /fork, персистентность sticky-lock на resume, запрет edit/redact в main; определить T1/T2 и поведение W3 — иначе схема падает в вечный дедлок при первом отпуске владельца.
