# Gateway deafness insurance contour (R4)

Продолжение `rtx5090-gateway-deafness-2026-11-14.md` (R1–R4). R1+R2 — в этой ветке
(`elk/gateway-deafness`). R3 — `elk/matrix-sync-token`. П9 (armed-approval) —
`elk/armed-approval-watch`. Остальное — этот документ: что ещё не построено и какие
решения принадлежат Вл, а не коду.

## Слои контура

**L1 — сенсор немоты (не построен, маленький).** Сердцебиение гейтвея
(`gateway-heartbeat`, ~15с) доказывает живой event-loop, но НЕ приёмный путь:
rtx5090 14.11 писал heartbeat, будучи глухим к Matrix. Проверяемый пульс приёма уже
есть у matrix-адаптера (`_last_sync_ts` обновляется КАЖДЫМ long-poll-ответом, пустым
в том числе — простои в чатах его не ломают). Минимальная реализация:
heartbeat-watcher дописывает в файл карту `platform -> age_seconds_since_receive_pulse`
(только для адаптеров, публикующих `receive_evidence_age()`; у остальных — поле
`unknown`, и отсутствующее доказательство НЕ трактуется как смерть). Это данные, не
действия — риск нулевой, можно лить сразу.

**L2 — наблюдатель (существует как muscle-скрипт узла).**
`~/.hermes/scripts/gateway-watchdog.py` (timer 30с): crash-loop revert + hang-детектор
(heartbeat stale >90с ×2), бюджет рестартов 2/30мин, freeze-файл. Третий детектор —
DEAF-STALL: unit active, heartbeat свежий, но receive-pulse одного из включённых
платформ старше порога (порог заведомо > long-poll timeout, для matrix — >120с) →
решение как у hang: лог-решение в SHADOW, действие только при включённом
`WATCHDOG_HANG_ACTION`. Вопрос доктрины: скрипт живёт на узле, а не в форке —
«чинить в форке» требует переноса его в `scripts/` форка с установкой через
`hermes update`; иначе сенсор L1 питает данные, которым неоткуда эволюционировать.

**L3 — действия.** Рестарт по бюджету уже есть; для DEAF-STALL честнее сначала
per-platform heal (адаптер переживает `create_adapter`-retry — R1 уже различает
healable/fatal), и лишь затем рестарт процесса. Порядок: сенсор → heal → рестарт →
freeze (человек).

## П9 — armed-approval (закрыто кодом, форма — тот же класс, что R1)

`elk/armed-approval-watch`: ambiguous-отправка карточки получила наблюдателя
(late-success → timeout-notice, late-failure → ровно один текстовый `/approve`
фолбэк с дедупом по центральному queue+ledger, decline → молчание). Остаток П9,
который кодом не закрыт: **armed-ход не переживает рестарт** (`pending_approvals` в
state.db доживают до `expired`, никто не будит владельца «я ждал решения, гейтвей
перезапустился, команда НЕ выполнена»). Это работа boot-sweep-семейства (как
resume-interrupted): при старте разобрать pending/expired-записи, назначенные чату, и
выдать notice в исходный чат. Делать в ветке или слить в AGENCY-контур — решить Вл.

## П7 — pet-profile offline > N (доктрина, не код)

Юнит с `Restart=on-failure` и чистым `exit 0` не рестартуется никогда; painter глох
на двое суток без единой тревоги. Общее правило контура: **каждый юнит, от которого
зависим чей-то inbound-транспорт, обязан иметь сигнал живности в L2** (порт-проба или
heartbeat-файл), иначе это не «дежурный сервис», а тихая точка отказа. На узле
rtx5090 — менять `Restart=` и вешать пробу порта; в форке — правило в доктрину
контуров (этот абзац).

## Решения, требуемые от Вл

1. L1-сенсор: делать в форке сейчас (мелкий, безопасный) — или ждать слияния R1–R3?
2. L2: переносить watchdog-скрипт в форк (канон + доставка `hermes update`) или оставить muscle узла?
3. Шаг-2 hang-детектора (SHADOW → активный рестарт): включать по статистике 2–3 дней или ждать отдельного слова?
4. Boot-sweep для armed-approvals: отдельная ветка или часть AGENCY-активации?
