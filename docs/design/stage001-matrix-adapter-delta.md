## Перечень дельт (D1–D13)

Формат: что / где / у кого / риск наивного слияния. «Идентично» = нулевая дельта, проверено построчно через diff предок→HEAD.

- D1. Reply-context fetch (`_fetch_reply_origin` + `_extract_reply_context`: подтягивание оригинала ответа в тред-контекст, парсинг reply-«pill» `> <@bot:srv>`). Оба адаптера. Идентично. Риск: нулевой; важно не «сливать» его заново — он уже в каноне и в 6 местах канальных тестов (`test_matrix_reply_ownership.py` и др.).
- D2. @room-патч. Вход: `MATRIX_REACT_TO_ROOM_MENTIONS` + `_is_bot_room_mentioned` (команда только когда человек начал тело с `@room`/`@all`; флаг `m.mentions.room` как транспортный артефакт игнорируется). Выход: `MATRIX_ALLOW_ROOM_MENTIONS` + `_has_outbound_room_mention` → `m.mentions.room=True`. Оба адаптера, идентично. Риск: нулевой.
- D3. E2EE / recovery key (bootstrap cross-signing, запись ключа в `MATRIX_RECOVERY_KEY_OUTPUT_FILE` 0600, profile-scoped чтение). Поведение идентично; на каноне функции вынесены в `plugins/platforms/matrix/recovery_key.py` (чистый move). Риск: наивное слияние создаёт два экземпляра одних функций (локально + импортируемые) — расхождение при будущих правках.
- D4. Thread-метаданные (`MATRIX_AUTO_THREAD`, `session_scope` auto|room|thread, `_thread_root`, threading-маршрутизация ответов). Идентично. Риск: нулевой.
- D5. Метка консоли `⎇ <имя>:` при отправке. Ни в одном адаптере её нет: декорирование живёт в ядре на границе публикации адаптеров (`gateway/branch_prefix.py` + `gateway/run_adapters.py`, коммит `6aa226f51b`; immutable-имя `93e10c890c`). Есть только на rtx5090 (ноды на разных rev ядра). Риск: при копировании win-адаптера «в канон» метка не поедет никогда — она не в слое; при обновлении win метка появится автоматически с ядром, и это нужно проверять лентой комнаты, а не файлом.
- D6. Транспортные наблюдения §16.9 (`TransportObservationMixin`, `_record_transport_observation` до всех gates, `_maybe_reconcile_transport` после dispatch, `_current_sync_batch`, новый sibling `transport_observation.py`). Только rtx5090. Риск: средний — mixin в MRO перед `BasePlatformAdapter`; без ядра-партнёра (`session_ingress_burst` и пр.) класс просто не соберётся.
- D7. `serial_receive_loop = True` на классе адаптера — ингрейс-серализация (следующий sync только после возврата обработчиков текущего), потребитель — `gateway/session_ingress_burst.py` на rtx5090. Только rtx5090. Риск: высокий — это поведение приёмной очереди; перенос флага на старое ядро win = тихий no-op, копирование win-строки в канон = потеря сериализации и возврат burst-гонок.
- D8. `delete_message` через redaction (#62) — включает `cleanup_progress` для tool-progress-пузырей. Только rtx5090. Риск: низкий (аддитивно).
- D9. Approval TTL: дефолт `MATRIX_APPROVAL_TIMEOUT_SECONDS` читается из общего `approvals.timeout` (`_default_approval_timeout_seconds`), фолбэк 300. Только rtx5090. Риск: низкий, но заметен оператору (таймауты согласуются с конфиг-ключом).
- D10. Контракт реестра платформ в `register()`: канон объявляет `platform_hint` (adapter_hint.py), `SEND_ENTRY_KWARGS` (send_targets.py), `DASHBOARD_CARD`, `env_overrides`/`ENV_ENABLE_CREDENTIALS`/`AUTHZ` (gateway_env.py — туда переехали `allowed_users_env`/`allow_all_env`); win-версия передаёт `allowed_users_env`/`allow_all_env` аргументами и не имеет hint/dashboard/env-строк. Только rtx5090 (ядро-контракт `3c3f85a0d0` и др.). Риск: самый высокий. Наивный merge win-версии в канон тихо теряет allowlist-проводку (ядро больше не читает эти kwargs — они объявлены в `gateway_env.AUTHZ`): бот начинает слушать незнакомцев; обратное направление ломает dashboard-карточку и prompt-hint.
- D11. Импорт-контракты с ядром: канон импортирует публичный `ssrf_redirect_guard`, win — приватный `_ssrf_redirect_guard`; плюс переезд `_env_number`/`_csv_set` в `env_config.py` и `_is_bare_media_filename` в `media_filenames.py`. Файл win на новом ядре падает на импорте; файл канона на старом ядре win — тоже (нет new-siblings/имён). Риск: высокий — любое частичное перетаскивание «куском файла» сломано по построению; синхронизировать надо парами (адаптер+ядро).
- D12. Instance-identity (#54): `device_name` при password-login и `_acct_id` crypto-пикла берутся из `hermes_cli.identity.instance_label()`. Только rtx5090. Риск: средний — на win после обновления изменится имя устройства/ключ пикла Olm-аккаунта: E2EE-сессии сбрасываются, требуется переверификация/девайс-ки, иначе «undecryptable» на ленте.
- D13. Model picker: usage-window строки (`picker_row_suffix`, `plan_line`) — только rtx5090. Риск: низкий.

Совокупно: 13 проверенных позиций; 4 из них (D1–D4) — нулевые дельты, 9 реальных — все принадлежат rtx5090, ни одна не принадлежит win. Отдельно к адаптеру: локальные uncommitted правки win (`gateway/run_config_loaders.py`, тест busy-mode) — не адаптерные, но при обновлении win их надо проверить и осмысленно похоронить или завести отдельным коммитом (на win уже висит autostash `stash@{0}` от 13.10 — признак, что автообновления там терлись о локальные правки).
