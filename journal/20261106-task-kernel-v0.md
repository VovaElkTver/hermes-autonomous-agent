## Что построено

**Состояние задачи — строка в state.db** (`tk_task`), не память агента:

```
ready → running → wait_human / wait_event → running → … → done | cancelled
```

- очередь = ORDER BY seq внутри chat_id; «список есть список», классов задач нет;
  wait-human — обычное состояние прохода, а не порода задачи (поправка Вл принята).
- `on_owner_message(chat)` — цикл обхода: голова в wait_human → done, следующая
  ready → delivered → снова wait_human. Очередь цикличная по требованию Вл:
  после вмешательства человека задача может уйти в running или ждать другого события.
- `emit(event_id)` — именованные события для wait_event-задач (многоразово,
  «сколько угодно раз»); failures of delivery оставляют задачу в RUNNING
  (не теряется, ретрай решает вызывающий).
- delivery — детерминированный subprocess `hermes send -t <target>` (как
  controller/alerts.py): ноль LLM-ходов на уведомление.

**Мост в шлюз** (`gateway/task_bridge.py` + 4 строки в
`BasePlatformAdapter._enqueue_text_event`): входящий текст владельца продвигает
голову очереди его чата. Fail-open (любая ошибка — в лог, messaging-path не
ломается), выключатель env `HERMES_TASK_BRIDGE=0`, при пустой очереди — один
COUNT(*) и выход. Сlash-command (`/…`) триггером не считается.

**Тулза агента `task_queue`** (tools/task_tools.py): actions create_batch /
status / skip / emit / cancel. `create_batch` создаёт N задач ровно по числу
items и стартует голову. Тулза зарегистрирована в `_HERMES_CORE_TOOLS`
(коммит `78a09f3a67`) — доступна в CLI, Matrix и всех hermes-* бандлах
(вердикт Вл: «надо и в cli и в матрикс… по сути не должно быть разницы»).

## Гаты/ограничения v0 (честно)

1. **Платформа доставки** — строка грамматики `hermes send -t`; по умолчанию
   `matrix:<chat_id>`. Ядро платформонейтрально (урок «матрикс-нейтральности»).
2. **wait_event пока ручной**: события регистрируются тулзой из хода;
   автопривязка к hermes_events Registry (пробуждение по таймеру/файлу/webhook
   без хода) — следующий шаг v0.1.
3. **Ретрай доставки** не автоматизирован: failed-delivery остаётся в RUNNING
   до ручного skip/emit.
4. Бюджетов/DAG/приоритетов сознательно НЕТ — минимальный механизм по SOUL §44.

## Инцидент, который поймал тестом

Первая версия регистрировала тулзу через wrapper `def register(): registry.register()`.
`discover_builtin_tools()` AST-сканирует модуль на **топ-левел** вызов
`registry.register(...)` (имя получателя литерально `registry`) — wrapper
пропускался, тулза не всплывала на поверхности. Ловится только end-to-end
проверкой surface через model_tools; фиксын коммит `6cb54ec863`.
