## Механизм (корень №1, whole-tree save)

`save_config()` по умолчанию `merge_existing=False`: пишет in-memory дерево целиком.
Штатный вызывающий делает `load_config(); mutate; save_config(config)`; между load и
save другой процесс добавил ветку — whole-tree write её молча стирает. Все callers
save_config (approval, mcp, gateway/config, secrets, setup, plugin_capabilities) —
leaf-правки, никто не удаляет секции намеренно (проверено чтением каждого).
`rebase_for_save` закрывала это только для frozen-worker (_three_way) и
merge_existing-вызывающих.

Фикс: `_preserve_concurrent_branches` в горле (config_worker_save.py). Правило
провенанса: живая ветка восстанавливается, если её НЕТ в последнем дереве, которое
ДАННЫЙ процесс грузил/сохранял (`_LAST_EXPANDED_CONFIG_BY_PATH`) — вызывающий не мог
удалить то, чего не видел. Виденную и убранную ветку не воскрешает — намеренное
удаление сохраняется. Рекурсия по mapping'ам; списки/скаляры — вызывающий побеждает
(контракт _merge_partial_save). Fail-open: любая внутренняя ошибка = старая семантика,
никогда не блокирует save.

## Механизм (корень №2, гвард читает как записи)

`plugins/config-protection` в free-text инструментах (terminal/execute_code)
блокировал ЛЮБУЮ строку, упомянувшую защищённый путь: `grep` по собственному
конфигу падал. 21.11 это стоило два сбитых прогона разведки. Фикс: блок по
записывающему контексту строки (>>, tee, sed -i, cp/mv/rm/touch/chmod,
write_text, open(...,'w'), patch, save_config, atomic_config, of=). path-arg
инструменты (patch/write_file/edit) блокируются безусловно как раньше. Перечень
намеренно избыточный: сомнительная строка = block (прежнее поведение).
